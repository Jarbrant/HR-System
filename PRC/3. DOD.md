# PRC/DOD.md
HR-System — DoD (Definition of Done)

Syfte:
DoD är vår “mållinje”. Den gör att alla trådar vet exakt när något är klart.
Om DoD inte är uppfylld → då är uppgiften inte klar, även om det “ser ut att funka”.

Gäller för:
- UI (admin/employee/manager/system + UI/pages)
- Worker (worker/)
- AI-regler (ai-rules/)
- Dokumentation som styr arbetet (PRC/)

---

## A) Grundkrav (gäller ALLT)
1) **Senaste sanning är känd**
   - Antingen: Anders har klistrat in hela filen
   - Eller: repo + commit är angivet
   - Om inte → stoppa och be om senaste sanning.

2) **Scope är respekterad**
   - Bara det som står i AO/PRC får ändras.
   - Inga “sido-fixar” utanför scope.

3) **Inga nya nycklar/ny struktur utan AO**
   - Inga nya storage-keys
   - Ingen ny datamodell
   - Om det behövs → skriv som Risk/Behöver beslut.

4) **Fail-closed**
   - Om något saknas/är trasigt → stoppa hellre än att gissa.
   - Tydligt felmeddelande för användaren.

5) **Rollregler hålls**
   - SYSTEM_ADMIN = steward-läge (read-only)
   - ADMIN/MANAGER får bara göra det deras sidor säger
   - EMPLOYEE kan bara göra sin del

6) **Säker textvisning**
   - Allt som visas för användaren ska vara “säkert” (ingen osäker text-injektion).
   - (I praktiken: sidan ska inte kunna råka visa körbar text som data.)

---

## B) UI-DoD (för sidor)
UI-ändring är klar när:
- [ ] Sidan laddar utan röda fel i konsolen vid normal användning
- [ ] Basflödet fungerar (klicklista i Testplan)
- [ ] Fel-läget fungerar (t.ex. trasig data → stopp + tydligt fel)
- [ ] Read-only roll kan inte spara/ändra
- [ ] Inga brutna länkar (404) till scripts/css
- [ ] Nya texter är begripliga för en 12-åring (kort, tydligt)

**Leverans måste innehålla:**
- [ ] Hel fil (inte små patchar)
- [ ] Ändringslogg (max 8 rader)
- [ ] Testnoteringar (vad du klickade)
- [ ] Risk/edge-cases (kort)

---

## C) Worker-DoD (för worker/)
Worker-ändring är klar när:
- [ ] Den gör exakt det den ska göra — inget mer
- [ ] Den läcker inte data i loggar
- [ ] Den accepterar bara det format som kontraktet säger
- [ ] Om input är trasig → returnera tydligt fel (inte “halv-resultat”)
- [ ] Samma input ger samma typ av output (stabilitet)
- [ ] Inga “placeholder-svar” eller tomma fält som förstör UI

**Leverans måste innehålla:**
- [ ] Hel fil
- [ ] Ändringslogg (max 8 rader)
- [ ] Testnoteringar (enkla prov-anrop eller test-sida)
- [ ] Risk/edge-cases

---

## D) AI-Rules-DoD (ai-rules/)
AI-regler är klara när:
- [ ] Strukturen är lätt att förstå (index → v1 → mappar)
- [ ] Det finns en tydlig “källa” för format (formats/)
- [ ] Det finns tydliga regler för kvalitet/variation (rulesets/)
- [ ] Det finns tydliga nivåer/steg (steps/levels)
- [ ] Ändringarna gör skillnad i resultat (inte bara “mer text”)

**Viktig regel:**
- Om UI kräver ett visst format (t.ex. fråga + svarsalternativ) → reglerna måste hjälpa till att hålla det formatet.

---

## E) QA-DoD (P0/P1/P2)
När något levereras ska det finnas en kort QA-check:

### P0 (måste fixas före merge)
- kraschar sidan / allt blir tomt / kan inte använda
- fel roll kan spara
- data försvinner eller skrivs sönder

### P1 (bör fixas snart)
- otydliga felmeddelanden
- små buggar som stör flödet
- variation/quality sviktar i AI-resultat

### P2 (nice-to-have)
- små förbättringar, städning, bättre texter
- prestanda/struktur som inte påverkar användaren nu

---

## F) Klar-signal (vad tråden ska skriva när den är klar)
När DoD är uppfylld ska tråden avsluta med:

“KLAR enligt DoD.
- KRAV uppfyllda: (ja/nej + kort)
- Testat: (lista 3–7 klicksteg)
- Risk/edge-cases: (max 3 punkter)
- Inga nya keys/datamodell: bekräftat”
